QUOTA_429_V1 — daily upload limit

A fourth processing state, alongside IN-3 / IN-4 (working), FAIL-2 / FAIL-5 / FAIL-6 (failed), and the reveal. It is NOT a failure. Nothing broke, nothing was lost, and there is nothing to retry. The handler ships before the backend can return 429, so until Commit 3 part 2 it is inert.

The state

Amber, not coral. Coral is the failure register in this product and this is not a failure.

That is today's limit

We have not started reading this one, so nothing is in progress. Come back tomorrow and upload it again.

One control only. No retry, because a retry would be refused. No spinner, and pollForResult is never called, which is the infinite-spinner bug this state exists to avoid.
Why the copy says “upload it again” and not “we will read it tomorrow”

This is the honesty question in this state, and it decides the copy.

The refused report does not queue itself. By the time process-report returns 429, the browser has already uploaded the PDF to storage and inserted the reports row. What the 429 prevents is the report_queue insert. So the row sits at status='uploaded' and nothing will ever pick it up, not tomorrow, not ever.

Copy that said “come back tomorrow and we will read it” would be a promise the system does not keep. Hence “upload it again”, which is true.
The FE cannot clean up the orphan row. Migration 0021 made reports.status non-client-writable, so the browser cannot mark it. Only the backend can. Flagged for Commit 3 part 2, see below.
